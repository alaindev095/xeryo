# Xeryo website

Corporate website for **Xeryo**, a technology company whose first and only active product is **Umunara Internship**, a platform helping TVET students in Rwanda discover internship opportunities and connect with participating companies.

This site introduces Xeryo and the product and sends visitors to the real Umunara Internship application. The application itself (dashboards, sign-in, student and company portals) is a separate product and is not part of this project.

Stack: HTML5, CSS3 and vanilla JavaScript. No frontend framework. One small zero-dependency Node script builds the static site.

---

## 1. What is in the site

| Page | File | Purpose |
|---|---|---|
| Home | `index.html` | Who Xeryo is, the first product, principles, vision |
| About | `about.html` | Company story, approach, starting point |
| Ventures | `ventures.html` | The single active product and its status |
| Umunara Internship | `umunara-internship.html` | Product landing page that points to the application |
| Contact | `contact.html` | Email-based contact for schools, companies, partners, general |
| 404 | `404.html` | Custom not-found page (`noindex`) |

There is **no contact form**. Contact works through `mailto:` links, which is honest and needs no backend. A form can be added later once a form service is chosen (never put private keys in frontend code).

### Why there is a build step

HTML pages share a header, footer and metadata. The build script fills those in and writes everything crawlers need (title, description, canonical, Open Graph, JSON-LD, sitemap) as **static HTML**, then validates the result. Nothing is generated by JavaScript in the browser. The browser JavaScript only handles the mobile menu and a subtle scroll reveal; the site is fully readable and navigable without it.

## 3. Run it locally

Requires [Node.js](https://nodejs.org) 18 or newer (check with `node --version`). No `npm install` is needed.

```bash
npm run dev
# open http://localhost:8080
```

`npm run dev` runs a **preview build** (adds `noindex`, blocks crawlers in `robots.txt`, uses `http://localhost:8080` for absolute URLs) and serves `dist/`. Without npm:

```bash
node scripts/build.mjs --preview
node scripts/serve.mjs
```

Open pages through the local server, not by double-clicking the HTML files: links are root-relative (`/about.html`). Edit a source file, run the build again, refresh.

## 4. Configuration: what you must fill in

All real-world values live in **`site.config.json`** (or as environment variables, which win over the file):

| Setting | Environment variable | Used for |
|---|---|---|
| `siteUrl` | `XERYO_SITE_URL` | Canonical tags, Open Graph URLs, JSON-LD, sitemap, robots |
| `appUrl` | `XERYO_APP_URL` | Every "Open the application" link |
| `contactEmail` | `XERYO_CONTACT_EMAIL` | Contact page, footer, Organization schema |
| `social.*` | (file only) | Footer links and `sameAs` in schema |

```json
{
  "siteUrl": "https://www.your-real-domain.rw",
  "appUrl": "https://your-real-app-address",
  "contactEmail": "name@your-real-domain.rw",
  "social": { "linkedin": "https://www.linkedin.com/company/your-page" }
}
```

Rules enforced by the build:

- **`siteUrl`** is required for a production build. It must be `https://`, a bare origin with no trailing path, and not a placeholder such as `localhost` or `*.example`. Choose the preferred hostname once (with or without `www`) and use it consistently; every canonical, sitemap entry and schema URL is derived from this single value.
- **`appUrl`**, **`contactEmail`** and each social link are optional. When empty, the related links and sections are **left out of the HTML** (no dead links). The Umunara page then shows a plain note that the application link is not published yet, and the Contact page says details are being finalised. The build prints a warning listing what is missing.
- `npm run build:strict` turns those warnings into failures, useful as a pre-launch gate.

### Changing the production domain

Edit `siteUrl` (one place), rebuild, redeploy. Nothing else in the code contains the domain. Then, in Google Search Console and Bing Webmaster Tools, add the new property and resubmit the sitemap.

### Configuring the Umunara Internship link

Set `appUrl`, rebuild. The link appears on the homepage, Ventures page, Umunara page, Contact page and footer.

### Updating contact information

Set `contactEmail`, rebuild. The Contact page, footer and Organization structured data update. Verify the mailbox exists and is monitored before launch.

## 5. Editing content

- **Page copy:** edit the page's `.html` file. Text is ordinary HTML.
- **Title, description, URL path:** the JSON block in the `<!--meta { ... }-->` comment at the top of each page. Keep titles under about 60 characters and descriptions under about 155. The build warns about long ones and fails on duplicates.
- **Navigation, footer, shared call to action:** `partials/header.html`, `partials/footer.html`, `partials/cta.html`.
- **Colours, type, spacing:** `css/variables.css`.
- **Conditional blocks:** `<!--IF:APP-->...<!--/IF:APP-->` (shown only when `appUrl` is set), `<!--IFNOT:APP-->...<!--/IFNOT:APP-->`, and the same for `EMAIL` and `SOCIAL`.
- **Brand images:** `python3 tools/generate-brand-assets.py` (needs `pip install pillow`) regenerates the social image and icons. The SVG favicon and wordmark are plain files you can edit directly.

### Adding or removing a page

1. Create `new-page.html` with a meta block (copy from another page) and add its name to `PAGES` in `scripts/build.mjs`.
2. Link to it from navigation or content.
3. Add a `<url>` entry to `sitemap.xml`. Remove the entry if you delete a page.
4. Rebuild. The build fails if the sitemap and the set of indexable pages disagree, if a canonical is wrong, or if any internal link is broken.

Update a page's `<lastmod>` date in `sitemap.xml` only when its content meaningfully changes.

## 6. Deployment

### Recommended: Netlify

It serves `404.html` automatically with a real 404 status, supports headers and redirects from `netlify.toml`, gives free HTTPS and handles custom domains. Vercel and Cloudflare Pages work equally well; `vercel.json` is included. GitHub Pages works only with a custom domain at the root and has no header or redirect configuration, so it is a weaker fit.

**Steps (Netlify, via Git):**

1. Push this folder to a GitHub repository.
2. In Netlify: **Add new site, Import an existing project**, pick the repository. The build command (`node scripts/build.mjs`) and publish directory (`dist`) come from `netlify.toml`.
3. Under **Site configuration, Environment variables**, add `XERYO_SITE_URL` (your final `https://` origin), and `XERYO_APP_URL` and `XERYO_CONTACT_EMAIL` when known. Or commit them in `site.config.json`.
4. Deploy. Branch and pull-request previews build in preview mode (`noindex`), so they never compete with production.

**Without Git:** run `node scripts/build.mjs` locally with the variables set, then drag the `dist` folder into Netlify's manual deploy area.

> A production build **fails on purpose** until `siteUrl` is a real domain. While you do not have one yet, use `npm run build:preview` (noindex) for review deployments. Never launch publicly from a preview build.

### What is configured where

| Setting | Where |
|---|---|
| Canonical tags, sitemap, robots sitemap line, schema, social tags | In code (`siteUrl`) |
| Security and cache headers, `/index.html` to `/` redirect, 404 handling | In code (`netlify.toml` / `vercel.json`) |
| Buying the domain, DNS records | Domain registrar |
| Attaching the domain, HTTPS certificate | Hosting provider |
| `www` to non-`www` (or the reverse) redirect | Hosting provider domain settings |
| Search Console and Bing verification and sitemap submission | Those tools (see `SEO.md`) |

### Custom domain, HTTPS and redirects

1. Buy a domain from a registrar of your choice (not done for you).
2. In Netlify: **Domain management, Add a domain**. Follow the DNS instructions (either point the registrar's nameservers at Netlify, or add the records it shows at your registrar).
3. Set the **primary domain** to the same hostname you put in `siteUrl`. Netlify redirects the other variant (`www` or apex) to it. This keeps one canonical hostname.
4. Under **HTTPS**, provision the free certificate and enable **Force HTTPS**.
5. Keep `siteUrl` identical to the primary domain, including `https://` and `www` or not.

### Custom 404

`dist/404.html` is served automatically by Netlify and Vercel for unknown paths with HTTP status 404. Cloudflare Pages does the same when a root `404.html` exists. The page uses root-relative asset paths so it renders correctly at any depth.

## 7. Validate the production deployment

After deploying, replace `YOUR_DOMAIN` below:

```bash
# Status codes: expect 200 for pages, 404 for the missing path
for p in / /about.html /ventures.html /umunara-internship.html /contact.html /robots.txt /sitemap.xml /favicon.ico /assets/images/xeryo-social-preview.png; do
  curl -s -o /dev/null -w "%{http_code}  $p\n" https://YOUR_DOMAIN$p; done
curl -s -o /dev/null -w "%{http_code}  (should be 404)\n" https://YOUR_DOMAIN/not-a-page

# HTTP and the other hostname variant should redirect to the canonical one
curl -sI http://YOUR_DOMAIN/ | head -n 3
```

Then check by eye and with free tools:

- View source on each page: one `<title>`, one description, a `canonical` pointing at the live address, no `localhost` or `%%`.
- `https://YOUR_DOMAIN/robots.txt` shows `Allow: /` and the sitemap line, and **no** `Disallow: /`.
- `https://YOUR_DOMAIN/sitemap.xml` lists exactly five live URLs.
- Google Rich Results Test and the Schema Markup Validator accept the homepage JSON-LD.
- Paste a page URL into a social sharing debugger (Facebook Sharing Debugger, LinkedIn Post Inspector) to confirm the image appears.
- Run Lighthouse (Chrome DevTools) or PageSpeed Insights on the live site.
- Submit the sitemap (steps in `SEO.md`).

## 9. Known limitations

- No contact form; contact is by email links.
- Pages use `.html` URLs (for example `/about.html`). This works identically on every host and locally. Hosts that also serve `/about` create a duplicate address, which the canonical tags resolve.
- CSS and JS are not fingerprinted, so they use short cache lifetimes (1 day) rather than year-long caching.
- The social image and icons are generated rasters; replace them with designer artwork if you commission a final logo.
- A `SoftwareApplication` schema is deliberately omitted (see `SEO.md`).
